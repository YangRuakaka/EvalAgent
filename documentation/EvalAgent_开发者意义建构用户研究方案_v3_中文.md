# EvalAgent 开发者意义建构用户研究方案

**方案版本：** 3.0  
**日期：** 2026 年 7 月 27 日  
**研究类型：** 有主持人的远程开发者意义建构研究  
**参与者投入时间：** 总计约 50 分钟  
**目标样本量：** 12 名新参与者  
**研究环境：** EvalAgent 与完整的 WebHarbor 安全复刻网站目录  
**核心循环：** 配置 - 比较 - 解释 - 重新配置 - 测试

## 1. 研究目的

本研究将 EvalAgent 视为一个用于配置和比较 GUI Agent 的意义建构（sensemaking）环境。研究的核心并不是考察参与者能否编写越来越详细的评估标准，而是理解人们如何构造有意义的 Agent 变体、比较由此产生的行为、解释不同 Agent 之间的相似与差异，并根据这些理解决定下一步应如何配置 Agent。

本研究围绕以下核心循环展开：

> 配置不同的 Agent → 比较它们的行为 → 解释相似点、差异与意外行为 → 修改配置 → 测试修改后的配置。

评估标准和 Agentic Judge 提供的证据仍可作为可选的意义建构资源，但参与者不需要完成强制性的标准编写任务，它们也不是本研究的主要结果指标。

本研究具有较强的**生态效度（ecological validity）**。这里的“生态”并非指自然环境，而是指参与者、任务和使用场景尽量接近预期的真实使用情境：Agent 开发者或评估人员在安全的部署前沙盒中，选择与个人兴趣或工作相关的任务，并创建他们真正希望比较的配置。本研究不在真实生产网站上运行，也不包含会产生现实后果的操作。

本研究用于补充而不是替代原有的受控组件研究。原研究为 structural alignment 和 evidence highlighting 的作用提供了探索性证据；本研究则考察围绕配置、比较、解释和重新配置所形成的完整人类意义建构过程。

## 2. 研究问题

**RQ1 - 配置：** 用户如何将一个任务、偏好或关切转化为多个他们认为值得比较的 Agent 配置？

**RQ2 - 比较式意义建构：** 当多个 Agent 执行相同任务时，用户如何理解它们的相似行为、差异行为与意外行为？

**RQ3 - 心智模型修正：** 比较式探索如何改变用户对“Agent 配置与 Agent 行为之间关系”的理解？

**RQ4 - 重新配置：** 用户通过比较获得的认识，会如何影响他们在后续 Agent 配置中保留、修改或测试的内容？

除上述问题外，本研究还考察哪些意义建构模式会跨领域重复出现，以及用户在哪些情况下仍然不确定或无法形成令人满意的解释。

## 3. 研究设计

本研究采用单一条件的混合方法设计。所有参与者均使用完整版本的 EvalAgent，不设置消融条件。原因是本研究旨在理解完整系统支持下的意义建构过程，而不是再次隔离某一个界面组件的效果。

每名参与者需要：

1. 选择一个对自己有意义的 WebHarbor 领域并提出一个任务。
2. 为同一个任务创建两个具有对比意义的 Agent 配置。
3. 说明他们预期这些配置将如何影响 Agent 行为。
4. 在 EvalAgent 中比较一个中性运行结果和两个带配置的运行结果。
5. 记录他们认为重要的相似点、差异、意外行为与解释。
6. 根据比较中获得的认识修改一个配置，或提出一个新的配置。
7. 检查修改后的运行结果，判断它支持还是挑战了自己的解释。

所有运行均保持 Agent 模型、任务、环境初始状态、工具和执行限制一致，只有参与者定义的配置发生变化。

## 4. 参与者与领域覆盖

### 4.1 参与者

招募 12 名具有 LLM Agent 开发、测试、使用或评估经验的参与者。适合的参与者包括：

- Agent 开发者；
- 评估或质量保证人员；
- HCI 或 AI 研究人员；
- 负责任 AI 审计人员；
- 具有较强技术经验的 Agent 用户。

优先招募工作中涉及 prompt/configuration 测试、行为比较、调试、质量保证或部署前评估的参与者。

参与者必须：

- 年满 18 岁；
- 能够使用英语完成研究；
- 愿意共享屏幕和录制音频。

参与者任务完成情况较差、不同意 EvalAgent 的判断、形成了错误解释，或者最终没有修改配置，均不构成排除理由。

### 4.2 带配额约束的自由选择

参与者可以从所有已准备好的 WebHarbor 网站中进行选择，但研究通过配额控制避免所有参与者都集中选择 Amazon。

在研究前表单中，每名参与者至少对三个网站进行排序，并为每个网站提出一个可能的任务。研究人员将参与者分配至其偏好排序中配额尚未满的网站。

当 N = 12 时，最终样本应满足：

- 至少覆盖 6 个不同网站；
- 至少覆盖 5 个宽泛领域类别；
- 任何单一网站（包括 Amazon）最多 2 名参与者；
- 任何单一宽泛领域类别最多 3 名参与者。

如果参与者排序中的网站均已达到配额，研究人员向其提供至少三个当前覆盖不足的网站供其重新选择。参与者可以拒绝自己不感兴趣的领域，而不应被迫接受。最终论文应报告每名参与者获得的是第一、第二还是第三志愿。

本研究不声称验证了 WebHarbor 的全部领域，只报告最终样本实际覆盖的网站与领域。

## 5. 任务与 Agent 配置

### 5.1 参与者自拟任务

任务应当是参与者感兴趣、具有现实合理性，并且允许存在多种合理策略的任务。任务应涉及搜索、比较、综合或推荐，而不是只需要一次明显点击即可完成的操作。

任务必须安全且可逆。任务不得要求：

- 完成购买；
- 完成预订；
- 注册课程；
- 下载文件；
- 发送消息；
- 修改账户；
- 执行其他可能产生现实后果的操作。

参与者不得输入真实凭据或敏感信息。

研究人员可以出于可执行性、安全性或明确终止条件的需要，对任务进行最小程度的修改，但不得代表参与者添加偏好或评估关切。最终任务文本必须得到参与者确认。

### 5.2 三个初始运行

针对同一个任务，研究准备三个运行结果：

1. **中性运行：** 只有任务要求，不增加额外偏好配置。
2. **配置 Agent A：** 任务加上参与者定义的第一项偏好、政策约束或行为优先级。
3. **配置 Agent B：** 任务加上另一项具有实质对比意义的优先级。

参与者应围绕自己的任务创建有意义的对比，而不是从固定 persona 列表中选择。可能的例子包括：

- 成本与便利性；
- 创新性与成熟可靠性；
- 速度与全面性；
- 大众流行度与专业适配性；
- 资源效率与模型能力。

每项配置应描述：当多个选项都满足明确任务要求时，Agent 应优先考虑什么。配置不得允许 Agent 为了偏好而忽略任务的明确要求。

### 5.3 运行结果生成

为避免把研究时间浪费在等待 Agent 执行上，三个初始 trajectories 在有主持人的正式研究前生成。每个配置均使用第一次技术上有效的运行。

如果 Agent 出现行为失败、循环、比较不完整或做出不理想的选择，只要运行过程在技术上有效，就应保留为研究数据。不得仅仅因为结果不够成功或不够有趣而重新运行。

参与者完成重新配置任务后，在正式研究中生成一条修改后的 trajectory。运行应立即开始，并在主持人进行初步回顾访谈时于后台执行。

如果运行生成时间超过正式研究剩余时间，则在 48 小时内安排一个标准化的 5-7 分钟异步跟进。修改后运行属于主要研究流程的一部分，而不是可选的 future work。

## 6. 数据收集

本研究收集六类主要数据：

1. **配置产物：** 参与者的任务、初始配置、选择该对比的理由，以及修改后的配置。
2. **预期数据：** 在看到 trajectories 之前，参与者对不同 Agent 行为的预测。
3. **交互数据：** 图导航、trajectory 切换、查看过的步骤、Judge 使用情况和带时间戳的界面操作。
4. **意义建构数据：** think-aloud 中的观察、解释、意外发现、不确定性，以及对配置与行为关系的说明。
5. **最终反思：** 参与者更新后的心智模型、偏好的配置、剩余不确定性和下一步配置。
6. **重新配置测试：** 修改后的配置、预期的行为变化、实际观察到的修改后行为，以及新运行是支持、挑战还是未能解决参与者的解释。

Agentic Judge 及其 evidence panel 仅作为可能触发意义建构的资源进行记录。研究不要求参与者至少调用多少次 Judge，也不要求其必须创建评估标准。

## 7. 研究流程

### 7.1 研究前活动，约 8 分钟

参与者在正式研究前完成一个简短表单：

1. 对至少三个 WebHarbor 网站进行排序。
2. 为每个网站提出一个现实可行的任务。
3. 针对最终分配的任务，编写两个希望比较的配置。
4. 解释为什么该对比对自己有意义。
5. 预测不同 Agent 可能出现的一至两个行为差异。

研究人员检查任务的可执行性和安全性，应用网站配额，向参与者确认任务，并提前生成三个初始 trajectories。

### 7.2 有主持人的正式研究，约 42 分钟

#### 阶段 1：欢迎与界面介绍，4 分钟

主持人说明：

> 我们研究的是人们如何理解和配置 Agent，而不是考察你能否找到唯一正确答案。Agent 可能出现意外行为，EvalAgent 的 Judge 也可能出错。请按照最有助于你理解这些运行结果的方式使用系统。

主持人演示如何：

- 切换 trajectories；
- 检查对齐步骤和分叉步骤；
- 打开步骤详情；
- 选择性地使用 Judge。

主持人不得演示或暗示一种“正确”的比较策略。

#### 阶段 2：初始心智模型，4 分钟

在展示运行结果前，主持人回顾参与者的配置并询问：

- 你希望每个配置分别鼓励什么行为？
- 你预计这些 Agent 在什么地方表现相似？
- 你预计它们在什么地方表现不同？
- 你最初认为哪个配置效果最好？为什么？
- 对上述预期的信心是多少？请使用 1-7 分评分。

#### 阶段 3：自由比较探索，15 分钟

参与者自由探索中性运行和两个带配置的运行。

开场提示：

> 请像你平时判断一个配置是否真正改变了 Agent 行为那样，自然地比较这些 Agent。请告诉我你注意到了什么、什么让你感到意外，以及你如何解释这些差异。

主持人可以使用以下中性追问：

- 你现在正在比较什么？
- 这个差异是有意义的，还是偶然或表面的？
- 你认为是什么导致了这种行为？
- 是否有任何行为与最初预期矛盾？
- 这些 Agent 是策略不同、结果不同，还是两者都不同？
- 你现在仍然无法确定什么？

主持人不得引导参与者关注某个特定 divergence、criterion 或 Judge verdict。

#### 阶段 4：意义建构图，5 分钟

参与者完成一份简短的 comparison map。针对每个 Agent，记录：

- 预期的配置含义；
- 实际观察到的策略；
- 与其他 Agent 的重要相似点；
- 重要差异；
- 最意外的行为；
- 当前对配置如何影响行为的解释；
- 对该解释的信心。

参与者还需注明每项解释属于：

- 有可见 trace 支持；
- 主要基于推断；
- 仍未解决。

该 comparison map 用于捕捉参与者的心智模型，不要求其编写正式的 evaluation criteria。

#### 阶段 5：重新配置与后台运行，5 分钟

主持人询问：

> 如果你还可以运行一个 Agent，你会在它的配置中保留或修改什么？你预期哪些行为会因此发生变化？

参与者可以修改 Agent A 或 Agent B，也可以创建新的 Configuration C。记录：

- 修改后的配置文本；
- 触发修改的观察；
- 预期的行为影响；
- 什么样的结果会挑战参与者当前的解释；
- 修改目的属于改进 Agent、测试一个假设，还是探索另一个 trade-off。

随后立即使用相同模型、任务、环境、工具和执行限制运行修改后的配置，唯一变化是配置文本。Agent 运行期间，主持人可以开始初步的回顾问题。

#### 阶段 6：检查修改后的运行，5 分钟

修改后的运行可用后，让参与者将其与最相关的原始运行进行比较：

- 行为是否按预期发生变化？
- 哪一项观察支持或挑战了你的解释？
- 修改后的配置是否成功隔离了你想测试的差异？
- 还有什么不明确？
- 你会保留、继续修改还是放弃这个配置？

研究人员记录重新配置测试是否：

- 支持；
- 部分支持；
- 反驳；
- 未能解决参与者关于配置与行为关系的假设。

如果运行在正式研究结束前仍不可用，则按照第 5.3 节安排标准化异步跟进。

#### 阶段 7：最终访谈，4 分钟

询问：

1. 多 Agent 比较帮助你理解了哪些单一 trajectory 无法揭示的信息？
2. 最重要的意外发现是什么？
3. 你对某个配置的理解是否发生了变化？
4. 哪项界面资源最影响你的解释？为什么？
5. 根据现有运行结果，还有什么是你无法判断的？
6. 这种 workflow 是否有助于真实的部署前 Agent 配置或测试？为什么？

最后收集：

- 参与者偏好的配置，允许并列；
- 对自己理解这些 Agent 的最终信心，1-7 分；
- 感知 mental effort，1-7 分。

## 8. 分析方案

### 8.1 主要分析单位：意义建构片段

主要分析单位是一个具有明确时间边界的 sensemaking episode：

> 触发因素 → 注意到的观察 → 解释 → 心智模型更新 → 配置行动 → 重新配置测试结果。

例如，参与者可能发现两个 Agent 得到相同结果，却使用了不同搜索策略；参与者将这种差异解释为速度导向配置的影响；在发现相反证据后降低信心；然后修改下一项配置，明确只有在哪些情况下才应优先考虑速度。

### 8.2 编码维度

对每个 sensemaking episode 编码：

- **触发因素：** graph structure、divergence、raw trace、outcome、Judge output 或跨运行比较。
- **意义建构对象：** 策略、动作、结果、失败、trade-off 或配置解释。
- **注意到的关系：** 相似、差异、矛盾、异常或不确定性。
- **解释行动：** 描述、比较、解释、质疑、测试或修正。
- **心智模型变化：** 确认、扩展、纠正、替换或未解决。
- **配置后果：** 保留、澄清、加强、减弱、合并、拆分或增加新配置。
- **重新配置结果：** 支持、部分支持、反驳、未解决或技术上不可用。

两名研究人员使用共享 codebook 独立编码全部片段，解决分歧，并报告结构化类别的编码一致性。

### 8.3 配置分析

分析参与者如何构造 Agent 差异：

- 抽象价值标签与可操作指令；
- 单一优先级与条件式或多目标配置；
- 相互对立的配置与互补性的实验探针；
- task-specific 与 cross-domain 配置概念；
- 用于优化行为的配置与用于测试假设的配置。

比较每名参与者的初始配置和修改后配置，分析比较式探索促使其增加、删除或明确了哪些内容。随后比较参与者预测的影响与修改后 trajectory 的实际行为。

单次修改后的运行不被视为因果证明。本分析关注的是用户如何提出和测试关于配置与行为关系的假设。

### 8.4 描述性指标

在参与者层面报告：

- 识别出的有意义相似点和差异数量；
- 明确表达的配置与行为关系数量；
- 被确认、被反驳或仍未解决的预期数量；
- 心智模型修正的数量和类型；
- 偏好配置是否改变；
- 是否提出修改后的配置；
- 修改后的运行是否符合预测；
- 信心变化；
- 哪些界面资源触发了 sensemaking episodes。

这些指标用于辅助解释定性结果。由于 N = 12，量化结果属于探索性结果，不用于对不同领域进行统计显著性比较。

### 8.5 跨领域与反例分析

通过 participant-by-domain matrix 区分：

- 至少在两个领域类别中重复出现的模式；
- 仅在特定领域出现的意义建构方式；
- 不同配置没有产生有意义差异的情况；
- 参与者提出了 trace 无法支持的关系解释；
- Judge 分散注意力或误导参与者的情况；
- 比较增加而不是消除不确定性的情况；
- 参与者决定不修改配置的情况；
- 修改后的配置未能产生预期行为的情况。

这些负面和未解决案例应作为正式研究发现报告，而不是作为噪声隐藏。

## 9. 预期贡献与主张边界

如果数据支持，本研究可以说明：

- 用户如何围绕对自己有意义的任务构造多个 Agent 之间的实验对比；
- comparative trajectories 如何帮助用户发现和解释行为差异；
- 意外行为和矛盾如何改变用户的心智模型；
- 意义建构如何影响后续配置选择和小规模假设测试；
- 这些过程的哪些方面会在已观察领域中重复出现或失效。

本研究不得声称：

- EvalAgent 证明某个配置导致了某种行为；
- 已经验证所有 WebHarbor 领域；
- 与控制条件相比，该 workflow 提高了配置质量；
- 参与者提出的解释等同于正式因果结论。

修改后的单次运行只是对参与者解释的一次探测，而不是受控的因果实验。参与者的解释应被视为基于可见行为形成的、可继续测试的假设。

## 10. 论文写作定位建议

新增研究应被定位为一个补充原受控组件研究的 ecological developer sensemaking study。

建议表述：

> 原受控研究考察了 structural alignment 和 evidence surfacing 如何支持比较与检查。新增的开发者意义建构研究则考察围绕这些组件形成的更完整人类过程：用户如何构造 Agent 变体、理解由此产生的行为、修正自己的心智模型，并在自选 WebHarbor 任务中测试后续配置。

结果章节应围绕意义建构循环展开：

1. 构造有意义的 Agent 对比。
2. 发现可对齐的相似点和差异。
3. 解释意外行为并修正心智模型。
4. 将理解转化为重新配置与测试。
5. 跨领域重复模式、不确定性与失效情况。

当参与者主动使用 criteria 时，criteria evolution 仍可作为次要观察结果出现，但不应继续组织整个研究或成为主要贡献主张。
