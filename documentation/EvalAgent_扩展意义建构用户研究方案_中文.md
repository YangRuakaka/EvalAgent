# EvalAgent 扩展意义建构用户研究方案（精简版）

**版本：** 6.0  
**日期：** 2026 年 7 月 29 日  
**参与者：** 12 名 GUI Agent 开发者、评估者或研究者  
**单场时长：** 约 50 分钟，最长 55 分钟  
**环境：** EvalAgent 与 WebHarbor 安全复刻站点

## 1. 研究目标

本研究观察开发者如何：

1. 为同一任务配置两个不同的 Agent；
2. 预测两个 Agent 会有什么行为差异；
3. 使用 EvalAgent 比较两条 trajectories；
4. 根据证据修改自己对 Agent 行为的解释；
5. 把新的理解转化成一次有目标的配置修改。

我们关注的不是参与者能否找到“正确 prompt”，而是 EvalAgent 是否支持他们形成更具体、有证据的 Agent 行为解释。

## 2. 研究问题

**RQ1：** 用户如何为同一任务配置两个有意义的 Agent variants，并预测它们的行为差异？

**RQ2：** 比较 trajectories 后，用户对配置与 Agent 行为关系的理解如何改变？

**RQ3：** 用户能否根据新的理解，做出一项有目标的配置修改并预测修改效果？

## 3. 参与者和任务

招募 12 名具有 LLM Agent、Browser Agent、GUI 自动化、prompting、调试或评估经验的参与者。

每位参与者从主持人提供的三个安全复刻站点中选择一个，并在五分钟内确定任务。全部研究应尽量覆盖多个站点和任务类型，避免所有参与者都选择同一购物任务。

任务需要：

- 可以在安全复刻站点中完成；
- 不涉及真实付款、发送消息或其他不可逆操作；
- 允许一种以上合理策略；
- 能在研究时间内运行。

## 4. 实验控制

参与者为同一任务配置 Agent A 和 Agent B。两者应只有参与者希望研究的配置不同。

以下设置保持一致：

- 模型和版本；
- 任务文本；
- 网站和初始状态；
- 工具与权限；
- 最大步数和 timeout；
- 执行环境。

系统保存 A、B 和修改后 Agent 的完整配置及 trajectories。

## 5. 研究流程

每个阶段只问一个核心问题，并记录对应的关键数据。

| 时间与阶段 | 用户做什么 | 必须问的核心问题 | 必须记录的数据 |
|---|---|---|---|
| 0–5 分钟：选择任务 | 选择站点、任务和停止条件 | **你选择了什么任务，做到什么程度算完成？** | 站点、任务文本、停止条件 |
| 5–10 分钟：配置 A/B | 为同一任务配置两个不同 Agent | **Agent A 和 B 最核心的配置差异是什么？为什么这个差异与任务有关？** | A/B 完整配置、精确 configuration diff、参与者描述的核心差异 |
| 10–20 分钟：事前预测 | 等待 A/B 运行并预测行为 | **在看到 trajectories 前，你预计 A 和 B 会有什么行为差异？为什么？** | 预期差异、原因、其他可能影响结果的因素 |
| 20–35 分钟：比较 trajectories | 使用 EvalAgent 查看相似、差异和证据 | **你发现了什么有意义的行为差异？哪段 trajectory evidence 支持你的判断？** | 用户查看的关键位置、发现的差异、引用的证据 |
| 35–38 分钟：总结理解 | 总结比较后的解释 | **这些证据确认还是改变了你原来的理解？现在你如何解释配置与行为的关系？** | 初始解释是否被确认、修改或仍不确定；比较后的解释 |
| 38–42 分钟：修改配置 | 对一个 Agent 做一项有目标的修改 | **你会修改什么？预计什么行为会改变？什么结果会支持或挑战你的解释？** | 修改前后 diff、修改原因、行为预测、支持或挑战条件 |
| 42–50 分钟：检查结果 | 查看修改后的运行并作出判断 | **修改后的行为是否符合预测？这让你保留、修改还是放弃原来的解释？** | 实际结果、支持/部分支持/挑战/无法判断、最终解释、剩余问题 |

初始 A/B trajectories 在两个运行都结束前保持隐藏，避免参与者根据一个 Agent 的早期结果修改另一个 Agent。

## 6. 主持原则

主持人按照表中的顺序，每个阶段只问一次核心问题。只有回答不清楚时才使用中性追问，例如：“可以再具体说一点吗？”不要暗示某个差异一定由 prompt、persona、配置或 Judge 导致。

## 7. 需要记录的数据

每场研究必须保存：

- 参与者背景和相关 Agent 经验；
- 任务、站点和停止条件；
- Agent A、B 的完整配置；
- 用户概括的 A/B 核心差异；
- 比较前的行为预测和原因；
- 用户查看和引用的关键 trajectory 位置；
- 用户发现的行为差异；
- 用户的解释是否被确认、修改或仍不确定；
- 修改前后的精确 configuration diff；
- 用户对修改效果的预测；
- 修改后的行为是否符合预测；
- 用户最终仍不理解的问题；
- 屏幕、音频、运行状态和技术失败记录。

## 8. 如何判断“理解加深”

如果用户在比较后能够：

1. 给出比事前预测更具体的配置—行为解释；
2. 引用明确的 trajectory evidence；
3. 区分重要差异、偶然细节和不确定因素；
4. 根据解释做出一项有目标的配置修改；
5. 提前说明什么结果支持或挑战自己的解释；

则视为 EvalAgent 支持了该用户对 Agent 行为的进一步理解。

这是一项过程和生态化研究。它可以说明用户如何使用 EvalAgent 加深或修正理解，但不能仅凭一次修改后的运行证明某个配置稳定地导致某种行为。

## 9. 分析方法

主要分析单位是一个完整的意义建构片段：

> 初始预测 → 查看证据 → 形成解释 → 解释变化 → 配置修改 → 运行结果

两名研究者对片段进行编码，重点记录：

- 用户发现了什么；
- 使用了什么证据；
- 解释是确认、修改还是仍不确定；
- 是否形成配置修改；
- 修改结果是支持、部分支持、挑战还是无法判断该解释。

最后报告常见模式、典型案例和失败案例。数量只做描述性统计，不进行不同网站之间的显著性比较。

## 10. 失败和停止规则

- **Agent 行为失败：** Agent 卡住、做出差的决定或任务失败。保留并分析。
- **技术失败：** 网站、浏览器、日志或执行环境故障。单独记录；只有尚未产生可解释 trajectory 时才允许重跑一次。
- **结果不符合预测：** 不重跑，作为重要的 negative case 保留。
- **超时：** 到 55 分钟仍未完成时结束现场研究，保存用户事前预测，并在运行结束后进行一次简短跟进。

## 11. 可以和不可以声称什么

可以声称：

- 用户如何配置和比较不同 Agents；
- 哪些 EvalAgent 资源支持或干扰了理解；
- 用户的解释如何变化；
- 用户如何把解释变成配置修改；
- 哪些情况仍然无法判断。

不可以声称：

- EvalAgent 普遍提高所有 GUI Agent 的成功率；
- 一次运行证明了配置与行为之间的稳定因果关系；
- 12 名参与者代表所有开发者和所有网站；
- Judge 或 criteria 是理解 Agent 的必要条件。
